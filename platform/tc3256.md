# ZX-UX on the TC3256, started from disk: a plan

The Timex TC3256 (Portuguese, 1986), started with the boot menu's
**"4. Disk start"**: ZX-UX runs on the machine itself, with its own
keyboard and screen (no terminal), in a **64 KB all-RAM map** (no ROM),
the SCLD's display at 4000h, and the FDD3000 as its disk server.

Sources (cited by short name):
- **MMU-guide**: `TC3256/SIM/DOCS/using_the_tc3256_mmu.md`, the MMU, ports `EEh`/`EDh`, the
  traps, disk-boot, the RAM disk (§3, §4, §6, §9.7, §9.9, §11);
- **Shadow-ref**: `ShadowROM_Technical_Reference.md` §11 (the boot menu) and `_v2` (§2, §3);
- **TIFDD-ref**: `TI_FDD_Technical_Reference_v2.md` §6 (the link), §11 (ports);
- **TOS-ref**: `TOS_Technical_Reference_v2.md` §2, §10, and `SIM/TOSDIS/dict/peer_map.md`;
- **HW-notes**: `platform/hardware-notes.md` §1 (what was found for ZX-UX).

## 1. The machine as Disk start leaves it

The boot menu's key 4 has TOS (on the FDD3000) `LOAD*` the 16 KB file
`BOOT` into 8000h, sets `EEh` = 80h (FIRMWARE), copies a 14-byte
relocator to 7F00h, pages out, and the relocator copies 8000h-BFFFh to
0000h and jumps to **0001h** (MMU-guide §9.7; Shadow-ref §11.2). Then:

| Z80 | What answers | Notes |
|---|---|---|
| 0000h-3FFFh | DRAM, physical 04000h-07FFFh ("disk-boot") | ours, read-write (WRITE_DISABLE not set) |
| 4000h-7FFFh | the SCLD's video RAM | the display at 4000h; contended |
| 8000h-FFFFh | DRAM, physical 08000h-0FFFFh | never moves |
| ports | FEh keyboard, border, beeper; FFh SCLD mode, interrupt inhibit; F5h/F6h AY; FDh RS-232; EFh the FDD3000 link; EEh/EDh the MMU (system mode only) | |

What makes it not quite a plain 64 KB machine:
- **Three trap addresses.** An opcode fetch at 0000h, 0008h or 0066h
  pages the shadow ROM in, even when the stage is RAM (MMU-guide §3,
  §11.3). RST 0 is a cold start (and clears the MMU); RST 8 is the shadow
  ROM's error / extended-command entry; 0066h is the network's NMI. Our
  image must never execute at those addresses, and no program may
  `RST 0`/`RST 8`.
- **0038h is ours**: IM 1 works directly (the SCLD's 50 Hz frame
  interrupt), no IM 2 table and no ROM bytes needed.
- **The rest of the 256 KB** (the RAM disk, 52 sectors of 4 KB) is seen
  only in system mode, one sector at a time at 3000h-3FFFh, with the
  shadow ROM at 0000h-2FFFh: code and stack at 4000h or above, interrupts
  off, the window closed before leaving (MMU-guide §6, §9.2).
- **The FDD3000 runs TOS**: a disk server on its own Z80, reached over
  the 6-bit link on port EFh with framed, checksummed blocks; commands
  are register snapshots (TIFDD-ref §6). Besides files (OPENF, READF...)
  it reads and writes **physical sectors**: RXSEC (1Bh: the host receives
  drive/track/sector C/D/E) and TXSEC (1Ch) (TOS-ref §10, peer map).
  TOS loads its overlays from drive A on demand (TOS-ref §2): drive A
  stays a TOS system disk.

## 2. The platform, in this tree's terms

A new `platform/tc3256/platform.inc` and a machine layer (as the
FDD3000's, `fdd3000/src`), nothing machine-named in the kernel:

| Setting | Value | Why |
|---|---|---|
| memory map | `memmap48.inc` | the ABI pins (6003h, 5BE4h, the window at F000h) decide it anyway |
| `HAL_SCREEN`, `HAL_SCR4000` | 1, 1 | the display is at 4000h: programs that draw run, the fixed kind too |
| `HAL_BLKDEV` | 1 | `/dev/fd0-3` through TOS's sector commands; `/dev/rd` the RAM disk |
| `HAL_VFS`, `HAL_SSXFILE`, `HAL_BOOTMNT` | 1, 1, 1 | as the FDD3000: ZXFS, TOS disks (the `tos` module), SDK programs from files |
| `HAL_SEQDEV` | 0 | the cassette was the ROM's: a clean-room tape driver is a project of its own (later, if wanted) |
| `HAL_FPMOD` | the float engine (`drivers/fp`) | no ROM calculator |
| `HAL_DEVFILES` | `tty:1 mem:2 fd0:8 ... rd:12` | |
| `mem_swapout`/`mem_swapin` | the RAM disk | §5 |
| text places | in the 16 KB low image | §4 |

Drivers, mostly shared:
- **console**: `drivers/screen64` as on the Spectrum, without the ROM: its
  own CLS and scroll (it already draws its own 4x8 characters), and an
  **8x8 font of our own** for the 32-column console (`HAL_FONT8` is the
  ROM's font today; the Sinclair font is not ours to copy);
- **keyboard**: a clean-room matrix scan and decode on port FEh in place
  of rom48's ROM calls; `libux/rbc/keyboard.asm` and its generated tables
  are a clean-room KEY-SCAN/K-DECODE already, checked against the ROM:
  share them (`drivers/` rather than libux, so both use one source);
- **clock**: the frame interrupt at 0038h calls `ktick` (`HAL_HZ` 50);
- **sound**: the beeper on FEh bit 4, clean-room (as `libux/rbc/beep.asm`);
  the AY at F5h/F6h later;
- **disk**: a host-side link driver for port EFh (the block tier: C0h
  command, D0h data, 80h status, ACK B0h, NAK E0h, the negated-sum
  checksum, retries), TOS's RXSEC/TXSEC for sectors and OPENF/READF/CLOSEF
  for the boot; the FDD3000 port's `fd.asm` is the controller side of a
  different dialect, but its framing ideas carry;
- **RAM disk**: the gateway (`CALL 0008h` with IY = 0, from code at or
  above 4000h), `EDh`, `EEh` bit 6, a 4 KB copy, window closed, `JP 0604h`.

## 3. Booting

**One file, `BOOT`.** Disk start's contract is 16 KB: the shadow ROM has
TOS load `BOOT` at 8000h and its relocator copies 4000h bytes to 0000h
(MMU-guide §9.7). ZX-UX is about twice that (the low image, then 5B00h
up to the end of the RAM file system), so `BOOT` is longer than 16 KB and
its first 16 KB fetch the rest **of the same file**:

1. Disk start brings in `BOOT`'s first 16 KB at 0000h and jumps to 0001h:
   the low image - vectors, the machine layer, the buffer cache, resident
   text (§4).
2. Its start-up code (SP high, IM 1, the link driver) opens `BOOT` on TOS
   and reads from offset 16 KB on: 5B00h up to the end of the root file
   system (kernel variables, the low kernel, the kernel, the text that did
   not fit low, the boot code, ITAB, the RAM file system), straight into
   place - none of it overlaps 0000h-3FFFh, where the reader runs, or the
   display.
3. It jumps to the kernel's `boot`; `/etc/init` mounts the system volume
   and runs its `rc` (`HAL_BOOTMNT`).

Phase 0 checks what LOAD* does with a file longer than 16 KB (whether it
loads it whole at 8000h - it would fit to FFFFh up to 32 KB - or stops,
or refuses: "Disk Boot File Error"). If the whole file is loaded, step 2
can copy from memory instead of reading; either way it is one file.

**One disk, in drive A.** Drive A must be a TOS system disk: the FDD3000
boots TOS from its tracks 0-3, and TOS loads its overlays from drive A
on demand (TOS-ref §2). A ZXFS cannot simply take the rest of that disk -
TOS would count those sectors free and write over them - so the system
volume is **a ZXFS inside a TOS file** on the same disk (`/etc/zxfs`, say,
made full size when the disk is built): its block device maps the
volume's sectors to the file's, through what the `tos` module already
knows of TOS's directory and allocation. A second drive, or a whole ZXFS
disk in B, is then only an option. (The simpler start, if phase 2 wants
one: a ZXFS disk in B.) `fdd3000/tools/tosfs.py` already writes TOS
disks; a `tc3256image.py` beside `fddimage.py` builds the system disk.

|---|---|
| 0000h-003Fh | restarts: 0038h the frame interrupt; nothing executable at 0000h, 0008h, 0066h; the other RSTs stop the program (`htrap`) |
| 0040h-... | the machine layer: link and TOS, RAM disk, keyboard, screen64, its fonts, vfs, ZXFS, ssx, clock |
| | the buffer cache (2 KB) |
| ...-3FFFh | text places `TXn` (`build.py place()`) |
| 4000h-5AFFh | the display (in use: no text place here, unlike the FDD3000) |
| 5B00h-5FFFh | kernel variables, low kernel, kernel stack (as now) |
| 6000h-... | the kernel; the text that did not fit; ITAB; **the arena**; the window at F000h |

Estimate (from today's sizes): the layer about 7-8 KB (the FDD3000's is
6.5 KB with vfs, ZXFS, ssx, the floppy driver; here the floppy driver is
the link driver, plus keyboard, screen64 and an 8x8 font), the buffers
2 KB, so 6-7 KB of text places; of the ~14 KB of resident text about
half fits low. **Arena about 17-18 KB at boot** (the Spectrum: 10.7 KB;
the FDD3000, which also has 4000h-5AFFh for text: 26.2 KB).

## 5. The RAM disk: the TC3256's own lever

52 sectors of 4 KB (208 KB), each the size of ZX-UX's window:
- **Process windows saved there, not in the arena** (`mem_swapout`/
  `mem_swapin`, the seam the plan made for this): a switch is gateway,
  sector, two 4 KB copies through 3000h (or an exchange), ~25 ms at
  3.5 MHz, interrupts off (one tick lost per switch: count it, as rom48's
  `tclk` counts the tape's). Frees ~4 KB of arena per waiting process,
  and the process table could grow beyond four.
- **`/dev/rd`**: the remaining sectors as a block device: a ZXFS volume
  (mount on `/tmp`, or a RAM root that outlives nothing but is large).
- ZX-UX owns the whole RAM disk: the shadow ROM's `SAVE!`/`LOAD!` files
  (sector 00h directory) are not kept.
- **Our own paging, later.** The shadow ROM is needed only to *enter*
  system mode (a fetch at 0008h with IY = 0 returns at once with PAGIN
  set); everything after - `EDh`, `EEh`, the copy, the exit through
  0604h - is our driver's code, no shadow ROM service involved. On that,
  the kernel can page as it likes in 4 KB units: windows of waiting
  processes (build 1), then whole process images and arena blocks (files,
  loaded programs) evicted to sectors and brought back on use, and more
  than four processes. The hardware's limit: a sector is never *executed*
  from in user mode (it is visible only at 3000h-3FFFh, in system mode,
  under the shadow ROM's 0000h-2FFFh), so paging is copying, not mapping.

## 6. Programs

This is a computer, not a terminal: programs draw on the screen and read
the keyboard directly. That works with `rcc --no-rom`: a bitmap
program asks call 41 where the display is and draws there; the fixed kind
draws at 4000h; `kbd_down` reads the keyboard rows (port FEh, as here).
What had to change was the switch: **`--ux` mixed two independent
choices**:

| | the ROM | the screen |
|---|---|---|
| what it decides | does the program call the 48K ROM (floats, BEEP, keys, printing)? | how does it reach the user: stream, console (the kernel's), bitmap (its own drawing, where call 41 says), fixed (its own drawing at 4000h)? |
| no switch | yes | undeclared: assumed fixed at 4000h |
| `--ux` (before) | no (clean-room runtime, call 42) | declared, from the program (`rbc`: pixels or not) |

Built (2026-11-20), for the SDK (`rcc`, `rbc`; the other compilers in
time); `--ux` is gone:
- **`--no-rom` / `--rom48k`**: whether the runtime may call the 48K ROM,
  recorded in the SSX1 flags (a free bit, say bit 5: "needs the 48K
  ROM"). `--no-rom` links the clean-room runtime (libux, floats through
  call 42); `--rom48k` the ROM's.
- **`--kind=stream|console|bitmap|fixed`**: the screen kind, declared as
  now (bits 3, 2-1); by default worked out from the program (as `rbc`
  does: pixels or not). With `console`, the width BASIC needs, 32
  columns (bit 4: `rbc` sets it for its console programs).
- Programs built before these switches (flags bit 3 clear) are what they
  were built as: they need the ROM and draw at 4000h.

**The kernel refuses, at load, what the machine cannot give** - each
need against a capability, each refusal saying which:

| The program | needs | refused where | message |
|---|---|---|---|
| `--rom48k`, or built before the switches | the 48K ROM | `HAL_ROM48K` 0 (FDD3000, TC3256 disk start) | "this program needs the 48K ROM" |
| kind bitmap | a screen it draws on itself | `HAL_SCREEN` 0 (a terminal: FDD3000) | "this program draws: it needs a screen" |
| kind fixed, or built before the switches | that screen at 4000h | `HAL_SCREEN` 0, or `HAL_SCR4000` 0 | as above, or "... at 4000h" |
| kind stream or console | nothing of the sort | nowhere | |

So on the TC3256 every `--no-rom` program runs, whatever its kind; on
the FDD3000 the `--no-rom` stream and console ones do; on the Spectrum
everything.

BASIC programs that draw read the character set at `CHARS` (the ROM's
font at 3D00h on a Spectrum): libux supplies the 8x8 font in the program
(as everything else of BASIC's support).

**The 8x8 font** is one data file (`drivers/font8/`: a text picture of
the 96 glyphs, turned into bytes by the build), used by the kernel's
narrow console and by libux alike; the platform names the one it uses
(`HAL_FONT8` becomes a file, not the ROM's address). Changing the font is
editing that picture, or pointing the platform at another file.

## 7. Phases

Each phase ends with its tests passing and the existing ones unchanged.

0. **The rig, and the unknowns answered.** The test machine is **FUSE**
   (the LoadZX fork, `TC3256/EMUL`): a full TC3256 - MMU, shadow ROM, Disk
   start, SCLD, the Timex FDD with TOS - driven by its automation harness
   as `fdd3000/test/fuse_shot.py` drives the TT3000 today (`FUSE_AUTOKEY`
   keys at given frames, `FUSE_AUTODUMP` memory and display dumps,
   `FUSE_AUTOQUIT`, its JSON results). A `fdd3000/test/fuse_shot.py`-like
   `tc3256run.py` boots a disk pair (menu key 4), types, and reads the
   screen back as text from the display file (the 4x8 font is ours: a
   decoder is a table). Where FUSE cannot show a thing easily (bytes on
   the link, a sector's contents), the Python side helps: the FDD3000
   model of `fdd3000/test/fddrun.py` can run TOS against the link driver
   alone. Questions to settle here, each with a test:
   - is port EFh usable in user mode (no gateway)? (The plan assumes yes:
     the TENET gate array decodes it; else the link goes through the
     shadow ROM's SENDBL/GETBL in system mode, from code at 4000h+.)
   - RXSEC/TXSEC exactly (registers, the block that follows, errors) on a
     ZXFS disk and on a TOS disk;
   - Disk start's file: a `BOOT` longer than 16 KB (loaded whole, cut, or
     refused), the entry at 0001h, what TOS and the shadow ROM leave set
     (SP, IM, interrupts, port FFh, EEh);
   - a TOS file's sectors: contiguous or not, and where the `tos` module
     finds them (for the ZXFS inside a TOS file);
   - the gateway with FIRMWARE=1, and an NMI at 0066h with no network
     fitted (none expected).
   **Done (2026-11-20)**: `tc3256/test/tc3256run.py` (a new TOS system
   disk from tomato, `BOOT` on it, Fuse's TC3256 with the Timex FDD, key
   4, memory read back; the link's traffic with `FUSE_LINK_TRACE`),
   `tc3256/test/probe.asm` and `test_probe.py`, and the host's link
   driver, `tc3256/src/link.asm` - phase 2's, already. The answers:
   - **Disk start** enters at 0001h with interrupts off, SP = FF56h, I = 0,
     EEh reading 80h (FIRMWARE) in user mode.
   - **`BOOT` longer than 16 KB**: the shadow ROM's `LOADP` asks TOS for
     4000h bytes of type CODE (its disassembly, `BOOT_KEY4_DISK`), so only
     the first 16 KB come - checked: bytes past them are not at C000h.
     The rest is ours to read through TOS: one file (§3).
   - **Port EFh works in user mode** (in Fuse; the gate array swaps bits
     4 and 7 between the sides, as the hardware does): no gateway needed
     for the disk. On hardware: to see once there.
   - **RXSEC** (1Bh; C, D, E = drive, track, sector ID): a 256-byte D0h
     block, then the reply (80h, status 0) - equal to the image's sector;
     **TXSEC** (1Ch): the D0h block first, then the command; read back
     the same.
   - **The gateway** with FIRMWARE: `CALL 0008h` with IY = 0 from C800h
     comes back in system mode (EEh 80h, the shadow ROM's `DI` at 0000h);
     `JP 0604h` returns to user mode with our RAM at 0000h as it was.
   - **A TOS file's sectors**: 1 KB allocation units listed in its
     directory entries (16 a 16 KB part; `tosfs.py`), contiguous only on a
     fresh disk - the ZXFS-in-a-TOS-file device maps through that list.
   - Still open: an NMI at 0066h with no network fitted (Fuse's TC3256 has
     TENET off: none came).

   with keyboard, screen64 without ROM, the 8x8 font, IM 1 clock; `BOOT`
   + `UNIX` loaded by Disk start; RAM file system only. Tests: boot to
   login, the golden sessions that need no tape, BREAK, the clock.
   **Done (2026-11-20)**: `platform/tc3256/platform.inc`, the layer
   `tc3256/src/hal.asm` (vectors, `tcboot`, the frame interrupt at 0038h,

   the `tos` module mounted; the system volume and its `rc`; SDK programs
   from disk. Tests: as `fdd3000/test` (zfs, boot, fsmod, tfs, ssx) on the

   `drivers/blk/blk.asm` (the buffer cache, `/dev/fdN`, seeks in sectors,

   for each handshake, and for the host to ask for a reply it has ready:
   the frame interrupt's whole work in the middle of a command loses it.
   At first a block crossed with interrupts off, and the clock lost the
   frames a disk command spanned (~70% of them through a long read).
   Since 2026-11-20 the interrupt is cut short instead while a command or
   a block is under way (`link.asm`: `lkon`/`lkei`, `lkbusy` a count, a

   T-states - and when the command is done, TOS waiting for the next,

   frame's end when the host had them on (the fork, 2026-11-20). The geometry is never probed

   system disk's two-sided flag (track 0 sector 0, 0Eh), else 40 tracks.

## 7a. On the back burner

- **Windows swapped to the RAM disk** (§5): 4 sectors for four processes,
  48 left for `/dev/rd`.
- **AY sound** (discussed 2026-11-20; not built). The AY-3-8912 at ports
  F5h (register) and F6h (data), clocked at about 1.7735 MHz (half the
  CPU's; `TC3256/SIM/DOCS/music_with_tc3256.md`). As a device, not ports
  written by programs: `/dev/ay`, writes of (register, value) pairs, a
  read describing it (its clock: programs turn hertz into periods with
  the machine's, not a constant); one process at a time (EBUSY), silenced
  (volumes 0, mixer off) when it closes, exits or is BREAKed. Platform:
  `HAL_AY`, the ports and the clock in `platform.inc`, `ay:13` in
  `HAL_DEVFILES` (the TS2068 the same ports; a 128K Spectrum FFFDh/BFFDh;
  none on the 48K or the FDD3000). libux: `ay_open`, `ay_reg`, `ay_tone`
  (hertz, from the device's clock), `ay_noise`, `ay_envelope`, `ay_off` -
  linked only when used; a program finds no chip and stays silent. Later:
  a queue the frame interrupt plays (tick, register, value), music while
  the program computes. BASIC has no sound but BEEP (TS2068 SOUND, 128K
  PLAY: a compiler matter). Test: Fuse's AY, its registers read back.

1. **The link**: our own driver on port EFh (phase 0 confirms the port
   works in user mode).
2. **Programs**: `--ux` replaced by `--no-rom`/`--rom48k` and `--kind`
   (§6), no compatibility kept; the kernel refuses a program needing the
   ROM where `HAL_ROM48K` is 0, and one that draws where there is no
   screen (`HAL_SCREEN`, `HAL_SCR4000`).
3. **The RAM disk**: ZX-UX owns it; our own driver; window swapping in
   build 1, more paging later (§5).
4. **The system disk**: one, in drive A: TOS, `BOOT`, and the ZXFS volume
   in a TOS file (§3).
5. **The 8x8 font**: an original one, one file, easy to replace (§6).
6. **`BOOT`**: one file (§3).
